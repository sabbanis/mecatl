Two agent-identity flows, compared

Four agents traced both documents hop by hop, checked them against the specs, and mapped the overlap. Neither document was treated as authoritative. This is what they found.

The shape both documents are describing

vMCP is a gateway, not an endpoint, so a tool call crosses two boundaries with different problems. Both documents cover both hops. They disagree about what travels across the first one.

The finding that decides the disposition

#321's Scenario B is built on a combination its own dependency forbids. That scenario needs a tsid claim to reach the user's stored credentials — and #321 concedes only ToolHive's authorization server can mint one, so a token minted by mecatl's own issuer cannot carry it. The exchange that would produce such a token is described only in #324.

Meanwhile #324 finds that a delegated token carrying act must not carry that same upstream reference, on least-privilege grounds — which breaks exactly the upstream_inject strategy Scenario B walks through.

So the two documents are not duplicating each other. One contains a worked example; the other contains both the mechanism that example presupposes and the rule that invalidates it. A contradiction like that has to sit next to the scenario it concerns.

Three blockers the code turned up, none of which either document had

Verification against four ToolHive branches found that the flow #324 proposes cannot run today — and for reasons other than the one #324 names.

1

No client that may use the exchange grant can be provisioned

The handler rejects public clients and requires the grant registered. Dynamic registration is the only provisioning path and it hardcodes clients as public, rejects any auth method but none, and permits only authorization_code and refresh_token. No static-client config exists. Identical on all four branches — so the shipped delegation path is reachable only through a test seam. Small fix: 50 to 100 lines.

2

The subject token must be issued by ToolHive's own server

Only a self-issued validator is wired; the multi-issuer validator has no callers and an open TODO. So an Okta or Keycloak access token cannot be the subject_token — which is precisely what #324's flow assumes it is. The harder of the two, and it has to be resolved first.

3

A delegated token keeps only the two trivial strategies

ToolHive's own consequence table lists XAA as surviving without the upstream session reference. It does not — XAA reads the stored upstream ID token and fails without it, exactly as the 3LO path does. So "confine delegation to XAA-capable backends" is not an available escape hatch, and the conflict #324 identified is sharper than it wrote. The genuine hatch, which neither document mentions: the STS-exchange and cloud strategies survive in their no-subject-provider mode by exchanging the delegated token itself.

Where they diverge, and what kind of divergence it is

disagree

What hop 1 actually presents

#321: mecatl's own child SVID is the inbound credential. #324: the SVID is only client authentication at a token endpoint, and the request carries a vMCP-minted token. Genuine, and #321 is underspecified here — it names no endpoint, grant type or client-auth method.

disagree

JWT-SVID or X.509-SVID

#321 scopes to JWT-SVIDs and calls X.509 "a real addition". #324 requires mTLS with the X.509-SVID. The specs favour #324 here: the X.509 path is ratified (RFC 8705), needs nothing from any external party, and makes issued tokens certificate-bound for free.

settled

Does the chain survive to hop 2 — no

#321 says mecatl's chain "rides the token the whole way". The code disagrees: the XAA strategy touches the identity at four points and never reads the claims map, so nothing mecatl puts in a claim reaches a backend. #324 is right. What survives is that the chain reaches vMCP, which is where enforcement belongs.

settled

Does the gateway already check SPIFFE IDs — no

#321's scenarios say the policy layer "already evaluates SPIFFE IDs in act.sub". The shipped mint puts the OAuth client_id there and does no SPIFFE parsing. SPIFFE appears in two files, both tests, matched by a string glob that would treat "banana*" the same way.

disagree

What SPIFFE buys

#321 adopts the identity half wholesale. #324 argues it buys two narrower things — no static client secret on disk, plus per-pod attestation — and that the trust-domain and rotation machinery may sit idle under the ID-JAG option.

both work

Where ID-JAG sits

#321 puts it at hop 2, vMCP to backend. #324's second option puts it at hop 1, mecatl to IdP to vMCP. Different hops, both coherent, same draft cited. Not a conflict.

both work

Instance or definition keying

They key different objects — #321 an SVID it mints itself, #324 a token vMCP mints. It only becomes a real conflict if the SVID is what gets presented, which is the first divergence above.

agree

Unattended work

Both land on client_credentials, and on an audit log that says the schedule did it rather than naming a user who was asleep. #324 states it as a grant, #321 as an owner record.

What exists in only one of them

Only #324

  • A delegated token breaks the plain-3LO, STS and cloud strategies — the ones serving most ordinary backends
  • Three competing values for act.sub are in flight, so no policy can be written yet
  • The two-hop decomposition itself, which makes #321's own scenarios legible
  • Hop-1 client-auth mechanics, and the ingress certificate-forwarding consequence
  • The fail-closed consent precondition, and why RFC 9068 §2.2 makes it reachable without may_act
  • Token caching as the reason to key on the definition
  • What the outbound path does today: a static header map baked in at dial time

Two corrections that came back at the author of #324

The client_id direction was wrong. #324 said the authorization server reads the SPIFFE ID out of the certificate. Both RFC 8705 §2 and the SPIFFE draft require the client to send client_id, with the server checking it against the certificate's URI SAN. Same resulting string, so the argument built on it survives; the sentence is fixed.

#321's case for a private chain claim is stronger than #324 credited. RFC 8693 §4.1 also restricts act contents to identity — non-identity claims "are not meaningful when used within an act claim". That forbids a per-hop scope snapshot inside act outright, which is a firmer reason than the one #321 argued for itself.

Still open, and worth more than either document settles

Joe Beda's review comment argues the root principal is authorizable, with rate-limit fan-out and user-store cases behind it. #321 still holds prior actors as audit-only. That sits on the same axis as #324's finding that the outermost actor slot holds exactly one party, so harness-level bounds must fold into scope at mint time. Neither document resolves it, and it is probably the most interesting question on the PR.
